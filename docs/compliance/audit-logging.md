# Audit and Compliance Logging Specification

Brief refs: A10.1 (p.27: "Each conversation must produce a structured log record", field table with retention), A10.2 (p.28: turn-level fields), A10.3 (pp.28-29: data encryption, access control, data retention and deletion, regulatory reporting), A11.3 (pp.31-32: "Every AI decision must be traceable to specific inputs, model versions, and KB entries"), A1.3 (p.4: Risk Committee concern "audit trail completeness for every AI-customer interaction with tamper-proof logging"), A4.3 (p.13: "Enhanced audit logging for all payment-related conversations"), A4.2 rule 1 (p.12: never "display, read out, or transmit full account numbers, card numbers, CVV, PIN, password, or Aadhaar numbers"), Part D Day 14-15 (pp.60-61: "Complete audit & compliance logging specification (interaction-level and turn-level schemas)"), Regulatory Reference Summary (pp.70-71). Machine-readable schema: `config/audit_log.schema.json`. Flow: `diagrams/audit-log-flow.mmd`. Checks: `tests/compliance/validate_compliance.py`.

**Status.** The system is specified, not built. Nothing in this document has been run or measured. The brief fixes: the 11 conversation fields with their retention, the 14 turn fields, AES-256 at rest, TLS 1.3 in transit, a separate key for PII fields, quarterly key rotation through an HSM, four access rules, automatic retention, deletion within 30 days including backups and derived data, deletion certificates, and four regulatory reports. Everything else here is a proposal and is marked as one, with a decision ID (D-181 to D-186, D-190). No regulation is quoted beyond the wording of the brief; legal detail the brief does not give is listed as a dependency in section 17.

## 1. Scope and principles

| # | Principle | Source |
|---|---|---|
| 1 | One conversation record per conversation and one turn record per speaker turn, written by the Audit and Telemetry Bus (component 11 of `docs/architecture/component-interfaces.md`) | A10.1, A10.2 |
| 2 | The brief's field names are used unchanged at the top level of each record. Every project addition sits under one object, `ext`, so a reader can always tell the brief's schema from the additions | D-181 |
| 3 | Redact first, then encrypt, then write. A value of handling class `never` (`config/entities.yaml`) is replaced by a placeholder at the Input Guard before any component or log sees it | A4.2 rule 1, RED-01 to RED-07 |
| 4 | Append-only. A record is never updated in place; a correction, an erasure or a late field (CSAT, outcome) is a new event that points at the record | A1.3 "tamper-proof logging", D-184 |
| 5 | Every answer the customer saw can be walked back to the KB entry versions, the prompt version and the model version that produced it | A11.3 accountability |
| 6 | Reading the log is itself logged | A10.3 "meta-audit trail" |
| 7 | Retention and deletion are enforced by jobs, not by people remembering | A10.3 "enforced automatically" |
| 8 | When the log cannot be written, the system fails closed (section 15) | FMEA #21, GR-REG-07, D-185 |
| 9 | Data stays in the India region | brief appendix p.70 (DPDP Act: "data localisation"), `docs/learning-pipeline/data-pipeline.md` section 3 |

| Field | Type | Description | Retention |

### 2.4 `resolution_status` rule

The brief lists four values and does not define them. Rule (D-181), evaluated when the conversation closes:

| Order | Condition | Value |
|---|---|---|
| 1 | An escalation record exists with outcome `handed_off` or `callback_scheduled` and the human channel has not yet closed the case | `escalated` |
| 2 | An escalation record exists and the human channel closed the case as resolved | `resolved_human` (written by a later `conversation.status_updated` event) |
| 3 | No live handoff took place and the outcome rule of `docs/metrics/kpi-framework.md` (KPI-G4, D-162) counts the conversation as resolved by the AI | `resolved_ai` |
| 4 | Anything else: abandoned, failed handoff, de-escalated without resolution, ended by the turn ceiling | `unresolved` |

Containment (KPI-G4) is `resolved_ai` with no escalation record, as D-162 defines it. A de-escalated record stays in `ext.escalations` with its outcome, so it remains visible to an auditor.

### 3.2 One record per speaker turn (D-181)

Every record carries all 14 brief fields. A field that does not apply to the speaker is null or an empty list, never absent, so a query never has to guess.

| Field | Customer turn | Agent turn | System turn |
|---|---|---|---|
| `raw_message` | sealed text | null | null |
| `intent_classification`, `sentiment_score` | filled | null | null |
| `entities_extracted` | filled | empty | empty |
| `knowledge_items_retrieved`, `retrieval_confidence` | empty, null | filled when retrieval ran | empty, null |
| `agent_response`, `response_generation_method`, `response_latency_ms`, `action_taken` | null | filled | null |
| `guardrails_checked`, `guardrails_triggered` | Input Guard and policy-side guardrails | Output Safety Layer, policy and tool-side guardrails | guardrails evaluated on the event, if any |

A human agent who joins after a handoff is written with `speaker: agent` and `ext.agent_kind: human`, so the brief's three speaker values are kept. A system turn records an event that is not a message: OTP sent or verified, session timeout, handoff state change, a breaker or lever change that affected the conversation.

### 5.1 Never logged

The values below never reach any log class, any buffer, any trace, any metric label or any handoff package. They are replaced before NLU by the typed placeholders of `config/entities.yaml`; the placeholder and the rule ID are logged, the value is not.

| Value | Rule | Placeholder | Brief source |
|---|---|---|---|

| CVV or CVC | RED-02 | `[CVV_REDACTED]` | A4.3 "CVV/CVC must never be requested, stored, or displayed" |
| Full Aadhaar | RED-03 | `[AADHAAR_REDACTED]` | A4.2 rule 1 |
| PIN, password, passcode | RED-04 (postal-code exception, D-35) | `[SECRET_REDACTED]` | A4.2 rules 1 and 5 |
| OTP typed in chat | RED-05 | `[OTP_REDACTED]` | A4.2 rule 5 |

### 5.2 Classification of every field

Classes: **P** personal content (sealed: redacted, then encrypted under the PII key on top of the store key); **Q** pseudonymous or quasi-identifying (store key, access restricted, erased on deletion); **O** operational, no personal data (store key).

| Field | Class | Stored form |
|---|---|---|
| `conversation_id`, `turn_id`, `ext.trace_id` | Q | plain UUID; random, not derived from the customer |
| `customer_id` | P | sealed in the stored record; a blind index (keyed hash) supports lookup (section 11) |
| `channel`, `authentication_level`, `primary_intent`, `resolution_status`, `guardrails_activated`, `model_version`, `turn_count`, `pii_detected` | O | plain |
| `csat_score` | Q | plain; nulled at 3 years |
| `raw_message`, `agent_response`, `ext.csat.comment` | P | sealed text |
| `intent_classification`, `sentiment_score`, `retrieval_confidence`, `knowledge_items_retrieved`, `response_generation_method`, `guardrails_checked`, `guardrails_triggered`, `response_latency_ms`, `action_taken` | O | plain |

| `ext.tool_calls[].args_masked` | Q | masked or reference values only; sealed |
| `ext.escalations[]`, `ext.escalation` | O, with `package_id` Q | plain; the package content is class P in LC-4 |
| `ext.versions`, `ext.experiment`, `ext.template`, `ext.retrieval`, `ext.guardrail_verdicts`, `ext.safety_verdict`, `ext.integrity`, `ext.retention` | O | plain |

## 7. Log integrity (proposal, D-184)

The brief asks for "tamper-proof logging" (A1.3) and gives no mechanism.

| Control | Design |
|---|---|
| Append-only store | Records are written once to storage with a write-once retention lock for the retention period. There is no update or delete path for a service identity; erasure is a key destruction plus an appended event (section 11) |
| Sequence numbers | `ext.integrity.seq` increases by 1 per record inside a conversation, starting at 0 for `conversation.started`. A missing number is a gap (`audit.gap_detected`), which is a finding in itself (FMEA #21) |
| Hash chain | `record_hash` = SHA-256 over the canonical JSON of the record with each sealed field represented by its `content_hash`. `prev_hash` is the `record_hash` of the previous record of the conversation. Because the chain covers the hash of the ciphertext and not the plaintext, destroying a key does not break it |
| Daily root | Once a day a hash tree over all `record_hash` values of the day is built, its root is signed with a key held in the HSM and written to a separate account with its own lock (`audit.root_published`). An auditor verifies any record against the root without trusting the log store's operators |
| Verification | Daily job: recompute every chain of the day and the root; weekly: a random sample of older days; before any regulatory export: the records exported. A failure opens an incident at SEV1 or higher (playbook section 2) |
| Time | Every component synchronises to two independent time sources. The component writes `timestamp`; the bus writes `written_at` and `clock_skew_ms`. Order inside a conversation is by `seq`, never by clock. Skew above 500 ms (proposal) raises an alert. Times are stored with an offset; reports use IST |
| Separation of duties | No single role can both write records and administer the store's lock or the signing key (section 9) |
| Late fields | CSAT, outcome class, `resolved_human` and review verdicts arrive after the conversation closed. They are appended events; the conversation record served to readers is the fold of the chain |

## 8. Encryption and key management

### 8.1 What the brief requires (A10.3 p.28, quoted)

| Brief requirement | Applied to |
|---|---|
| "All log data encrypted at rest using AES-256 encryption" | Every log class LC-1 to LC-8, the local buffers, the lookup index, backups and exports |
| "All log data encrypted in transit using TLS 1.3" | Component to buffer, buffer to bus, bus to store, store to reader, store to the learning pipeline, exports to a regulator |
| "PII fields additionally encrypted with separate key (double encryption)" | Class P fields of section 5.2: sealed under a PII data key, then stored under the store key |
| "Encryption keys rotated quarterly through hardware security module (HSM)" | Store keys and PII key-encryption keys; rotation events are logged (`key.rotated`) |

### 8.2 Key hierarchy (proposal, D-183)

| Key | Held in | Protects | Rotation |
|---|---|---|---|
| Root keys | HSM, never exported | The key-encryption keys below | Per the HSM policy of the Information Security Officer |
| Store key-encryption key, one per log class | HSM | Data keys of the store (first layer, all data) | Quarterly (brief) |
| PII key-encryption key | HSM, separate from the store keys and under a separate access policy | Per-customer PII data keys | Quarterly (brief) |
| Per-customer PII data key | Wrapped by the PII key-encryption key; one per `customer_id`; one per conversation for anonymous conversations | Class P fields of that customer's records (second layer) | Re-wrapped at each quarterly rotation; destroyed on erasure |
| Pseudonymisation key | HSM | The keyed hash that produces `customer_id` and the blind index | Not rotated in place (rotation would break joins); versioned, a new version applies to new customers. Proposal |
| Signing key for daily roots | HSM | Integrity of section 7 | Yearly, old public keys kept (proposal) |

Per-customer data keys are what make deletion reach backups and write-once copies: destroying one key makes that customer's sealed fields unreadable in every copy (section 11). The brief fixes AES-256 and does not name a mode; an authenticated mode is proposed and is a platform choice. Whether "rotated quarterly" requires re-encrypting stored data or re-wrapping data keys is not stated; re-wrapping is proposed and is a question for the Information Security Officer (section 17, AL-D3). NexBank's own channel encryption design stays dependency G-07 of `docs/guardrails/regulatory-mapping.md`.

### 9.4 Break-glass

| Aspect | Rule (proposal) |
|---|---|
| When | A stated need the standing matrix does not cover: a regulatory query about named conversations, an audit sample, a customer's own access request, a legal instruction |
| Who approves | Two people: the requester's function lead and one of the Data Protection lead or the Information Security Officer. The requester cannot approve. For restricted notes the AML Compliance lead must be one of the two |
| Scope | A list of `conversation_id` values or a query that returns at most 100 conversations; a time box of 4 hours; read only; no bulk export without a second approval |
| Record | `access.break_glass_opened` and `access.break_glass_closed` with requester, approvers, reason code, scope and the records actually read |
| Review | Every use is reviewed on the next working day by the role that did not approve it; uses are reported monthly to the Risk Committee |
| Emergency | During a SEV0 the Incident Commander may open break-glass with one approver; the second approval is obtained within 24 hours and its absence is itself an incident finding |

### 9.5 Reading of the customer-facing staff rule

The brief limits customer-facing staff to "anonymised, aggregated metrics" for log access. A human agent who receives an escalated conversation must see its context, or the customer repeats everything (A9.1 Context Carry-Over; D-04). The handoff package is therefore treated as service data pushed to the assigned agent, not as log access: the agent has no query interface to LC-1 to LC-3, sees only the package of the case assigned to them, and that view is logged like any other access. This reading is part of D-186 and is listed for Risk Committee confirmation.

### 9.6 Enforcement

Access is decided by attributes (role, queue assignment, case assignment, incident membership, purpose, time box) at the store's query layer, not in the dashboards. Sealed fields are decrypted only for a cell that allows content, by a service that holds no standing key access itself and logs the decryption. Access rights are reviewed quarterly by the Data Protection lead (proposal), and a query that returns no assigned conversation for a supervisor is denied and logged (`access.denied`, audit query AQ-12).

### 10.3 Enforcement

| Step | Rule |
|---|---|
| Clock start | The date the conversation closed (`ext.ended_at`). The brief does not say when the period starts (AL-D4) |
| Stamp | `ext.retention.delete_after` and `csat_delete_after` are written when the record is sealed |
| Daily job | Selects records past `delete_after` with `legal_hold` false; destroys the content (key destruction for sealed fields, removal of the record when the store lock has expired); appends `retention.expired`; writes a job report to LC-6 |
| CSAT at 3 years | `csat_score` is nulled by an appended event and `ext.csat.comment` is erased; the rest of the record continues to 7 years |
| Lock length | The write-once lock of each object equals its retention period, so the store cannot delete early and does not hold data late |
| Legal hold | A hold suspends expiry for the listed conversations (D-87). The hold has an owner, a reason and a review date; release resumes the clock |
| Proof | Audit queries AQ-07 and AQ-08 must return zero rows; the job report is evidence for the annual audit |

## 11. Deletion and right to erasure

### 11.1 What the brief requires (A10.3 p.28, quoted)

"Customer right-to-deletion requests processed within 30 days"; "Deletion includes all copies, backups, and derived data including model training data"; "Deletion certificates generated and stored for regulatory proof".

### 11.2 The conflict the brief leaves open

The same section requires a 7-year record of every conversation and deletion within 30 days of a request, and does not say which prevails. `data-pipeline.md` open item 4 left this to this document. Proposal (D-183), to be confirmed by the Data Protection lead, Legal and the Regulatory Compliance Manager (AL-D1):

1. On a verified request, **everything personal is erased inside 30 days**: message text, reply text, entity values, tool arguments, handoff package content, CSAT comment, `customer_id`, every derived dataset row, and every model that learned from the rows (D-104, D-157).
2. A **de-identified residual record** is kept to the end of its 7 years: the class O fields of section 5.2 (channel, authentication level, intent, resolution status, guardrail IDs, version tuple, counts, the integrity fields), with timestamps reduced to the hour and turn times kept as offsets. It can no longer be linked to a person by NexBank's AI systems. It is what lets the bank still show a regulator that a conversation took place, which guardrails fired and which versions answered.
3. Records under **legal hold** are not erased until the hold ends (D-87); they are listed on the certificate as held.

If Legal decides that the residual record is still personal data, the residual is removed too and the certificate says so; if Legal decides that statutory retention overrides erasure of content, step 1 is limited to derived data. Neither change needs a schema change.

### 11.3 Workflow

The agent's own part is small: it acknowledges the request, never claims immediate deletion, and routes it (case GR-REG-13-02; KB-FAQ-010, KB-REG-007). The rest is the deletion workflow owned by the Data Protection lead.

| Day | Step | Stores touched | Owner |
|---|---|---|---|
| 0 | Request received through an authenticated channel; identity verified at the level the bank requires for account changes; `deletion.requested` logged with a request id. The 30-day clock starts | LC-6 | Data Protection lead |
| 0 | Legal-hold check and scope: all conversations whose blind index matches the customer, in every channel | LC-6 | Data Protection lead, Compliance lead |
| 0 to 1 | Tombstone written for the pseudonymised id and its pipeline re-key (`deletion.tombstoned`). From the next snapshot (at most 24 hours) no dataset build contains the customer (QG-07). The conversations leave every review queue and dashboard drill-down | LC-6, learning pipeline | Data Protection lead, Data Engineering |
| 1 to 7 | Audit store erasure: the customer's PII data key is destroyed in the HSM (`key.destroyed`), which makes every sealed field unreadable in the primary store, replicas, write-once copies and backups at once; `customer_id` is erased; the blind index rows are deleted; handoff packages and CSAT comments are erased the same way; an `deletion.erased` event is appended to each chain and `deletion_state` becomes `erased` | LC-1 to LC-4, lookup index | Security Operations |
| 1 to 7 | Weekly purge of the learning stores: dataset revisions, feature and label stores, CSAT and outcome tables, experiment assignment tables, review-tool caches (`data-pipeline.md` section 9.2) | learning pipeline | Data Engineering |
| 1 to 20 | Models whose lineage includes a purged row are replaced through the deletion-only rebuild (D-157); the worst case is day 20 | models | NLU Team, ML Team |
| by 30 | Backups: index and learning-store backups expire (retention under 30 days); audit-store backups hold only ciphertext whose key no longer exists | backups | Data Engineering, Security Operations |
| by 30 | Human-channel and ticketing copies of the handoff package are deleted by their owners and confirmed to the workflow (AL-D5) | downstream systems | queue owners |
| by 30 | Deletion certificate generated, signed and stored (`deletion.certificate_issued`); the customer is told the request is complete | LC-6 | Data Protection lead |

### 11.4 Deletion certificate

| Field | Content |
|---|---|
| `certificate_id`, `request_id`, dates of request and completion, elapsed days | Proof of the 30-day duty |
| Subject | A keyed hash of the tombstone, never the customer's identity |
| Conversations | Count and `conversation_id` list |
| Stores | Each store with the action taken (key destroyed, rows deleted, expired) and the date |

| Held items | Anything kept under legal hold, with the hold reference |

### 11.5 Special cases

| Case | Rule |
|---|---|
| Anonymous conversation | No `customer_id` exists, so a deletion request cannot find it by identity. The customer may quote the conversation reference shown in the chat; otherwise the content, already redacted, expires on schedule. Such conversations are never training data (D-104) |

## 13. Audit queries

Pseudo-SQL over the logical tables `conversation_log` (LC-1), `turn_log` (LC-2), `tool_log` and `retrieval_log` (LC-3), `package_log` (LC-4), `access_log` and `integrity_log` (LC-5), `deletion_log` (LC-6). `ext.x` is written `ext_x`. A query that reads sealed fields is marked "content" and needs a matrix cell that allows it.

**AQ-01. Explain one answer (traceability, A11.3).** Which inputs, versions and KB entries produced the reply the customer saw at a given turn?

```sql
SELECT c.conversation_id, a.turn_id, a.agent_response,            -- content
       q.raw_message, q.intent_classification, q.entities_extracted,
       a.response_generation_method, a.ext_template, a.ext_policy_action, a.ext_reason_codes,
       a.knowledge_items_retrieved, a.ext_retrieval, a.guardrails_checked, a.guardrails_triggered,
       a.ext_safety_verdict, a.ext_tool_calls, a.ext_versions, a.ext_experiment
FROM   turn_log a
JOIN   turn_log q ON q.ext_conversation_id = a.ext_conversation_id
                 AND q.ext_turn_index = a.ext_turn_index AND q.speaker = 'customer'
JOIN   conversation_log c ON c.conversation_id = a.ext_conversation_id
WHERE  a.ext_conversation_id = :conversation_id AND a.ext_turn_index = :turn_index AND a.speaker = 'agent';
```

**AQ-02. Blast radius of a KB entry version.** Every customer-visible answer that cited a given entry version.

**AQ-05. Monthly summary (RPT-01).**

SELECT c.channel, c.primary_intent, COUNT(*) AS volume,
       SUM(CASE WHEN CARDINALITY(c.ext_escalations) > 0 THEN 1 ELSE 0 END) AS with_escalation_record,
       SUM(CASE WHEN c.resolution_status = 'resolved_ai' AND CARDINALITY(c.ext_escalations) = 0 THEN 1 ELSE 0 END) AS contained,
       SUM(CASE WHEN c.ext_complaint IS NOT NULL THEN 1 ELSE 0 END) AS complaints

**AQ-06. Complaint analysis (RPT-02).** Categories, and whether grievance information was given within 2 turns (GR-REG-03).

```sql
SELECT c.ext_complaint.category, COUNT(*) AS complaints,
       SUM(CASE WHEN c.ext_complaint.grievance_info_given_at_turn - k.first_complaint_turn <= 2 THEN 1 ELSE 0 END) AS grievance_info_in_2_turns,
       SUM(CASE WHEN 'ESC-002' IN (SELECT e.trigger_id FROM UNNEST(c.ext_escalations) e) THEN 1 ELSE 0 END) AS legal_threat

        WHERE speaker = 'customer' AND intent_classification.label LIKE 'CMP-%' GROUP BY ext_conversation_id) k
       ON k.ext_conversation_id = c.conversation_id
WHERE  c.ext_complaint IS NOT NULL AND c.ext_started_at >= :quarter_start AND c.ext_started_at < :quarter_end
GROUP  BY c.ext_complaint.category;
```

## 14. Traceability from an answer to its sources (A11.3)

The brief: "Every AI decision must be traceable to specific inputs, model versions, and KB entries"; "Accountability chain documented: who designed, who approved the model, who reviewed guardrails".

| Step | From | To | Where it is recorded |
|---|---|---|---|
| 1 | The text the customer saw | The agent turn record | `agent_response`, `turn_id` (query AQ-01) |
| 2 | The turn | Its inputs | The customer turn with the same `turn_index`: `raw_message`, `intent_classification`, `entities_extracted`, `sentiment_score`; the masked history is rebuilt from earlier turn records |
| 3 | The turn | The decision | `action_taken`, `ext.policy_action`, `ext.reason_codes`, `ext.escalation`, `ext.guardrail_verdicts` |
| 4 | The turn | The facts used | `knowledge_items_retrieved` and `ext.retrieval.kb_entry_ids` as `id@version`; each version is an immutable KB revision with its owner, approval chain and source reference (`docs/knowledge-base/kb-schema.md`); tool results by `reference_id` |
| 5 | The turn | The wording | `response_generation_method`, `ext.template` (template id, variant, version) and the `prompt_version`, whose bundle hash resolves in `config/system-prompt/manifest.yaml` to the six layer versions, their authors and approval chains |
| 6 | The turn | The models | `ext.versions.model_version` and `component_models`; each model version records its dataset versions, code version and base model (`data-pipeline.md` section 7) |
| 7 | The turn | The rules and parameters | `rules_version`, `registry_hash`, `parameters_version`; the registry and `config/parameters.yaml` name the owner and change process of each value |
| 8 | The versions | Who approved them | Gate G5 approvals of `safety-invariants.md` for the release; the RACI of `docs/risk/fairness-testing.md` section 8 for who answers for an error |
| 9 | The turn | Why two customers differed | `ext.experiment` (arm) and `ext.language`; no customer attribute is an input to a threshold (D-121) |

A conversation is replayable when steps 2 to 7 are complete. The share of agent turns with a complete version tuple and resolvable references is a proposed control metric (target 100 percent; a miss is an audit finding).

## 15. Failure behaviour when the audit bus is down (proposal, D-185)

Existing contracts: the bus is asynchronous with a local buffer and "Audit write failure on a high-risk action blocks that action" (`component-interfaces.md` row 11); FMEA #21 (log loss); GR-REG-07 with case GR-REG-07-01; the audit-gap alert at 50 percent buffer depth (`docs/guardrails/monitoring-dashboard.md` section 6). This section makes them complete. The rule behind it: **no customer-visible turn and no action without a durable record somewhere**.

### 15.1 Two kinds of acknowledgement

| Ack | Meaning | Needed for |
|---|---|---|
| Local durable | The event is on the component's encrypted local buffer and flushed to disk | Every turn |
| Bus durable | The bus has accepted and replicated the event | High-risk actions, before the tool is called (`tool.requested` pre-action record) |

### 15.2 Risk classes of actions

| Class | Tools and actions | Rule when the bus ack cannot be obtained |
|---|---|---|
| H1 change | Any write that changes an account, a card setting, a payment instruction or a profile: contact and address updates, nominee update, account upgrade, closure request, recurring payment set-up or cancellation, credit limit change, EMI conversion, card replacement, callback scheduling tied to an account | **Blocked.** The agent says honestly that it cannot complete the request now, offers a human, and never says the action happened (GR-REG-07, GR-SYS-01; case GR-REG-07-01). `result: blocked_audit` |
| H2 protective | `block_card`, `flag_fraud`, `send_credential_reset_link`, dispute and complaint ticket creation, any P0 or P1 handoff | **Not blocked by a bus outage.** Allowed with the local durable ack, because the card, ticket and queue systems are systems of record that journal the action themselves. If the local buffer is also unavailable the agent does not act; the customer is handed to a human at once. Blocking a card block during a fraud report would trade customer safety for log completeness |
| R read | Balance, statement, transaction and status look-ups; KB answers | Allowed with the local durable ack |

### 15.3 States

| State | Condition | Behaviour |
|---|---|---|
| A0 healthy | Bus acks inside its budget | Normal |
| A1 buffering | Bus unreachable or slow; local buffer below 50 percent | Turns continue from the local buffer. H1 blocked, H2 and R as above. `audit.buffering_started`; alert to the audit bus owner |
| A2 buffer pressure | Buffer at 50 percent (alert) and at 80 percent (page) | As A1. At 80 percent the Gateway stops opening new conversations on that node and routes them to healthy nodes |
| A3 no durable write | Buffer full, or the buffer disk failed, on every node that could serve the conversation | **Fail closed.** No model reply is generated. The customer gets the static status message and the human line (`TPL-SYS-STATUS-STATIC`, GR-SYS-01 last rung); an open P0 conversation is handed to a human with whatever package exists. The Gateway keeps a minimal counter of refused conversations. Opens an incident |
| A4 recovery | Bus back | Buffers replay in `seq` order; writes are idempotent on (`conversation_id`, `seq`); the chain is verified; any gap is logged as `audit.gap_detected` and reviewed. H1 actions are re-enabled only after the replay of the node has completed |

Buffer sizing (section 16): four hours of peak traffic at the current volume is about 741 MB in total across the nodes, so A3 should be reached only when both the bus and local storage fail. Sequence gaps, time spent in A1 to A3 and the count of `blocked_audit` actions are reported on the guardrail dashboard (DM-12 panel, audit gap row) and in the annual audit report.

Note for readers of `component-interfaces.md`: "Never block the customer turn" there describes the normal asynchronous path. It does not permit an unlogged turn; state A3 is the case it does not cover.

## 17. Payment-related conversations, and dependencies

For such a conversation: every tool call has a pre-action record with a bus ack; the integrity of its chain is verified daily rather than by sample; every read of it is reviewed; card data appears only as last four digits (GR-REG-05).
